**Система:** Ноутбук на базе 13th Gen Intel Core i5-13420H (Raptor Lake-H)  
**Операционная система:** Windows 10 Home Single Language x64 (Build 19045)  
**Роль отчета:** Руководство системного инженера по микроархитектурной оптимизации (Hardware & Microarchitecture Optimization Guide)  
**Дата аудита:** Октябрь 2026 г.

## 1. Паспорт аппаратной платформы (Hardware Passport)

На основе физического зондирования системы через Win32 API (`GetLogicalProcessorInformationEx`, `Win32_Processor`, `Win32_PhysicalMemory`, `Win32_VideoController`) получены точные аппаратные спецификации:

| Компонент / Метрика | Значение в системе | Архитектурная специфика |
| :--- | :--- | :--- |
| **Процессор (CPU)** | Intel Core i5-13420H | 13th Gen Raptor Lake-H (Intel 7 / 10nm Enhanced SuperFin, Model 0xBA, Stepping 2) |
| **Физические ядра** | 8 ядер (4P + 4E) | 4 Performance-ядра (Golden Cove/Raptor Cove) + 4 Efficient-ядра (Gracemont) |
| **Логические потоки** | 12 потоков | P-ядра: 2-way SMT (Hyper-Threading) = 8 потоков; E-ядра: 1 поток на ядро = 4 потока |
| **Частотная формула** | P: 2.10 – 4.60 ГГц; E: 1.50 – 3.40 ГГц | All-core Turbo: P-ядра ~3.8–4.2 ГГц, E-ядра ~2.8–3.1 ГГц (при PL1 = 45 Вт) |
| **L1D Cache** | 48 КБ на P-ядро (12-way), 48/32 КБ на E-ядро | 64-байтовая линия кэша; латентность 4–5 тактов; 3 порта загрузки по 256 бит |
| **L1I Cache** | 32 КБ на P-ядро (8-way), 64 КБ на E-кластер | Полоса декодирования: P — 6-wide (до 8 uops/такт), E — 2x 3-wide (до 5 uops/такт) |
| **L2 Cache** | 1280 КБ (1.25 МБ, 10-way) на P-ядро; 1280 КБ на весь 4-ядерный E-кластер | Выделенный L2 на каждое P-ядро; E-ядра делят 1.25 МБ L2 на четверых |
| **L3 Cache** | 12288 КБ (12 МБ Smart Cache, 8-way) | Неинклюзивный общий кэш (Victim Cache), кольцевая шина (Ring Bus) |
| **Оперативная память (RAM)** | 16 ГБ LPDDR4X-4267 (Micron MT53E1G32D2NP-046) | 128-битная шина (4x32-bit subchannels), пиковая ПСП ~68.26 ГБ/с (реал: 48–54 ГБ/с) |
| **Векторные расширения** | AVX2, FMA3, F16C, BMI1, BMI2, POPCNT, GFNI, VAES | 16 256-битных регистров `YMM0`–`YMM15`. AVX-512 аппаратно отключен. |
| **Графика (iGPU)** | Intel UHD Graphics (48 Execution Units, 1.40 ГГц) | Без выделенной VRAM, делит системную шину LPDDR4X с CPU. |
| **ОС / Планировщик** | Windows 10 Home (19045) | **Критично:** Windows 10 не имеет полной телеметрической интеграции с Intel Thread Director (ITD)! |

> [!IMPORTANT]
> **Вывод по вычислительному контуру:**  
> Интегрированная графика Intel UHD (48 EU) не имеет собственной видеопамяти и ограничена пропускной способностью системной LPDDR4X. Векторный блок CPU (AVX2 + dual 256-bit FMA) является **основным высокопроизводительным тензорным вычислителем** в системе. Обучение и инференс нейросетей должны быть скомпилированы и оптимизированы непосредственно под микроархитектуру Raptor Lake CPU.

## 2. Глубокий микроархитектурный анализ гетерогенных ядер

```
           +-----------------------------------------------------------+
           |                 12 MB Shared L3 Cache                     |
           +-----------------------------------------------------------+
                 |             |             |             |
     +-----------+             |             |             +-----------+
     |                         |             |                         |
+-------------------+   +-------------------+|   +-------------------+ +-------------------+
|   P-Core 0        |   |   P-Core 1        ||   |   P-Core 2..3     | | E-Core Cluster 4-7|
| 1.25 MB L2 (10w)  |   | 1.25 MB L2 (10w)  ||   | 1.25 MB L2 each   | | 1.25 MB Shared L2 |
| 48 KB L1D (12w)   |   | 48 KB L1D (12w)   ||   | 48 KB L1D each    | | 48/32 KB L1D each |
| CPUs [0, 1] (SMT) |   | CPUs [2, 3] (SMT) ||   | CPUs [4, 5, 6, 7] | | CPUs [8, 9, 10, 11|
| 2x 256-bit FMA    |   | 2x 256-bit FMA    ||   | 2x 256-bit FMA    | | 1x 256-bit FMA/E  |
| 32 FLOPs/cycle    |   | 32 FLOPs/cycle    ||   | 32 FLOPs/cycle    | | 16 FLOPs/cycle/E  |
+-------------------+   +-------------------+    +-------------------+ +-------------------+
```

### 2.1. Микроархитектура P-ядер (Raptor Cove / Golden Cove)
- **Топология:** Физические ядра 0, 1, 2, 3 $\rightarrow$ Логические процессоры `[0, 1]`, `[2, 3]`, `[4, 5]`, `[6, 7]`.
- **Конвейер:** 6-wide декодирование, ROB на 512 записей (Reorder Buffer), 12 портов исполнения.
- **Векторные FMA конвейеры:**
  - Порт 0: 256-bit FMA (Mul + Add) / Vector ALU.
  - Порт 1: 256-bit FMA (Mul + Add) / Vector ALU.
  - Пропускная способность: $2 \times 8 \text{ (FP32)} \times 2 \text{ (FMA ops)} = 32 \text{ FP32 FLOPs/такт}$.
- **Пиковая производительность 4 P-ядер:**
  $$\text{Peak}_{\text{P-cores}} = 4 \text{ cores} \times 4.0 \text{ GHz} \times 32 \text{ FLOPs/cycle} = \mathbf{512.0 \text{ GFLOPs (FP32)}}.$$
- **SMT (Hyper-Threading):** 
  При выполнении плотного FP32 GEMM регистровый файл и порты 0/1 перегружены. 1 поток на физическое ядро (4 потока всего) выдает максимальный IPC без перекрестных задержек L1D кэша. Использование 8 SMT потоков эффективно только тогда, когда алгоритм упирается в задержки выборки памяти (Memory Stalls / Cache Misses).

### 2.2. Микроархитектура E-ядер (Gracemont Cluster)
- **Топология:** Физические ядра 4, 5, 6, 7 $\rightarrow$ Логические процессоры `[8]`, `[9]`, `[10]`, `[11]`.
- **Конвейер:** Кластерный 2x 3-wide декодер, ROB на 256 записей, 5 портов ALU, 2 векторных порта.
- **Векторные конвейеры:**
  - 1x 256-bit FMA (или 2x 128-bit FMA) = $16 \text{ FP32 FLOPs/такт}$.
- **Пиковая производительность 4 E-ядер:**
  $$\text{Peak}_{\text{E-cores}} = 4 \text{ cores} \times 3.0 \text{ GHz} \times 16 \text{ FLOPs/cycle} = \mathbf{192.0 \text{ GFLOPs (FP32)}}.$$
- **Кэш L2:** 4 E-ядра **делят между собой один общий кэш L2 объемом 1.25 МБ** (в отличие от P-ядер, где у каждого свои 1.25 МБ). При многопоточном расчете матрицы в E-кластере потоки 8..11 конкурируют за полосу L2.

### 2.3. Коэффициент вычислительной асимметрии
$$\text{Asymmetry Ratio} = \frac{\text{Throughput}_{\text{P-core}}}{\text{Throughput}_{\text{E-core}}} = \frac{4.0 \times 32}{3.0 \times 16} \approx \mathbf{2.67 \times}.$$
Одно P-ядро выполняет векторные матричные вычисления в **2.7 раза быстрее**, чем одно E-ядро!

## 3. Оптимальный тайлинг кэша (GEMM Cache Tiling)

Для матричного умножения $C = A \cdot B + C$ ($M \times N \times K$) по методологии GotoBLAS / BLIS вычисления разбиваются на 5 иерархических циклов, отображаемых на регистры, L1D, L2 и L3.

```
Матрица A (M x K)                    Матрица B (K x N)
+-------------------+               +-------------------+
|                   |               |                   |
|   Mc x Kc Block   | (в L1D)       |   Kc x Nc Panel   | (в L2)
|                   |               |                   |
+-------------------+               +-------------------+
        \                                   /
         \                                 /
          v                               v
    +-------------------------------------------+
    | Микроядро (Register Tile Mr x Nr = 6 x 16) | -> YMM0..YMM11
    +-------------------------------------------+
```

### 3.1. Регистровый тайл (Microkernel $M_r \times N_r$)
Архитектура AVX2 предоставляет 16 векторных регистров `YMM0`–`YMM15`.
Каждый регистр вмещает 8 значений `f32` (256 бит = 32 байта).

Оптимальная схема распределения регистров — **$M_r = 6$, $N_r = 16$**:
- **Аккумуляторы $C$:** $6 \times 2 = 12$ регистров `YMM0`–`YMM11` (каждая строка шириной 16 элементов занимает 2 регистра YMM).
- **Вектор строки матрицы $B$:** 2 регистра `YMM12`, `YMM13` (загрузка 16 элементов строки $B_{k,:}$).
- **Бродкаст элемента матрицы $A$:** 1 регистр `YMM14` (`_mm256_set1_ps(A[i, k])`).
- **Свободный регистр:** 1 регистр `YMM15` (для конвейерной предвыборки / FMA-развязки).

**Арифметическая интенсивность микроядра:**
- На один шаг по $K$ выполняется $6 \times 2 = 12$ инструкций `_mm256_fmadd_ps`.
- Каждая операция считает $12 \times 8 \times 2 = 192 \text{ FLOPs}$.
- Требуется всего $6$ скалярных загрузок из $A$ и $2$ векторные загрузки из $B$ (всего $8$ загрузок памяти).
- Отношение: $\mathbf{24 \text{ FLOPs / load}}$ — конвейер полностью насыщен, утилизация FMA портов 0 и 1 приближается к 95%.

### 3.2. Тайл кэша L1D ($M_c \times K_c$)
- Физический размер L1D на P-ядре: **48 КБ**.
- Рабочий бюджет: не более **28–32 КБ**, чтобы исключить вытеснение линий стека, дескрипторов и строк $B$.
- Формула: $M_c \times K_c \times 4 \text{ байта} \le 32768 \text{ байт}$.
- **Оптимальные значения:**
  - $K_c = 256$ (кратно шагу unroll, $256 \times 4 = 1024$ байта = 16 кэш-линий по 64 байта).
  - $M_c = 24$ (кратно $M_r = 6$: ровно 4 микроядра).
  - Объем буфера $A$: $24 \times 256 \times 4 = \mathbf{24.576 \text{ КБ}}$ (ровно 51% от 48 КБ L1D). Идеально размещается в L1D без конфликтов ассоциативности (12-way).

### 3.3. Тайл кэша L2 ($K_c \times N_c$)
- Физический размер L2 на P-ядре: **1280 КБ (1.25 МБ)**.
- Рабочий бюджет под упакованную панель $B$: **384–512 КБ** (оставляя резерв под код, буфер $C$ и системные нужды).
- Формула: $K_c \times N_c \times 4 \text{ байта} \le 524288 \text{ байт}$.
- **Оптимальные значения:**
  - При $K_c = 256$:
  - $N_c = 384$ (кратно $N_r = 16$: ровно 24 микроядра).
  - Объем буфера $B$: $256 \times 384 \times 4 = \mathbf{393.2 \text{ КБ}}$ (30.7% от 1.25 МБ L2). 
  - Панель $B$ полностью удерживается в L2 на протяжении прохода по всем строкам $M_c$.

### 3.4. Тайл кэша L3 (Smart Cache 12 МБ)
- Общий объем: **12288 КБ (12 МБ)**, разделяемый между всеми ядрами.
- При работе 4 P-ядер эффективный бюджет на поток: $\sim 2.5 \text{ МБ}$.
- Внешний цикл по $N$ нарезается блоками $N_{\text{outer}} = 768 \dots 1536$, гарантируя, что подматрицы не выбивают L3 и не вызывают постоянных обращений к LPDDR4X.

### 3.5. Выравнивание структур данных (Data Alignment)
- Все тензорные буферы должны иметь строгое **64-байтовое выравнивание** (размер кэш-линии Raptor Lake).
- В Rust: `#[repr(align(64))]` или аллокация через `alloc_zeroed(Layout::from_size_align(bytes, 64))`.
- Предотвращает:
  1. *Cache line splits* (штраф 12–18 тактов на невыровненную загрузку через границу 64 байт).
  2. *False Sharing* при параллельной записи результатов в многопоточных редукциях.

## 4. Балансировка гетерогенных ядер (P-cores vs E-cores)

### 4.1. Проблема запаздывающего ядра (Straggler Effect)
При наивной параллелизации через OpenMP (`#pragma omp parallel for`) или Rayon (`par_iter()` с дефолтным чанкованием):
- Задача делится поровну на 12 потоков (по 8.33% на поток).
- 4 P-ядра (8 потоков) завершают свою долю за время $T$.
- 4 E-ядра выполняют ту же долю за время $2.7 \times T$.
- **Результат:** Быстрые P-ядра простаивают в spin-wait барьере синхронизации **63% времени**! Пиковая производительность падает вдвое по сравнению с расчетом только на P-ядрах.

### 4.2. Специфика Windows 10
В отличие от Windows 11 22H2/23H2, операционная система **Windows 10 (Build 19045)** не обладает полноценной поддержкой Intel Hardware Feedback Interface (EHFI / Thread Director v2). Планировщик Windows 10:
1. Может случайным образом назначить высоконагруженный AVX2 поток на E-ядро (CPU 8..11).
2. Мигрирует потоки между P и E ядрами, сбрасывая горячие кэши L1D и L2.
3. Применяет агрессивное энергосбережение к фоновым потокам.

**Решение:** Программная фиксация аффинитета (Thread Affinity Pinning) и управление качеством обслуживания (QoS) через Windows API.

---

### 4.3. Три рекомендуемых режима параллелизации

```
+-----------------------------------------------------------------------------+
|                           СТРАТЕГИИ ПУЛА ПОТОКОВ                            |
+-----------------------------------------------------------------------------+
| Режим 1: P-Core Max Compute | Режим 2: Динамический Rayon | Режим 3: Асимметричный   |
| (4 или 8 потоков)           | (8-10 потоков)              | Конвейер (Pipeline)      |
|                             |                             |                          |
| Фиксация на P-ядрах [0..7]  | P-ядра + 2..4 E-ядра        | P-ядра: GEMM / Тензоры   |
| 0% задержек на барьерах     | Мелкий шаг (Work-Stealing)  | E-ядра: I/O, Токенизация |
| Максимальный Turbo Boost    | Утилизация ~85% системы     | 100% перекрытие фаз      |
+-----------------------------------------------------------------------------+
```

#### Режим 1: «Чистый P-Core Compute» (Рекомендуется для максимальной скорости GEMM)
- **Конфигурация:** Пул ровно на **4 физических P-ядра** (потоки привязаны к CPU 0, 2, 4, 6) либо **8 SMT потоков** (CPU 0..7).
- **Маска аффинитета:** `0x00FF` (все P-потоки) или `0x0055` (только основные логические процессоры P-ядер).
- **Преимущества:**
  - Тепловой бюджет (TDP 45W) полностью отдается 4 P-ядрам. Частота держится на отметке 4.1–4.3 ГГц.
  - Нулевой оверхед на ожидание медленных E-ядер.
  - Отсутствие конкуренции за L3 с E-кластером.

#### Режим 2: «Адаптивный Work-Stealing» (Rayon на 8–10 потоков)
Если необходимо задействовать всю мощность машины:
- Размер пула: **8–10 потоков** (4 P-ядра с SMT = 8 потоков + 2 E-ядра).
- Никогда не использовать статическое разбиение (`par_chunks`)!
- Использовать **Rayon с динамическим шагом**:
  ```rust
  use rayon::prelude::*;
  
  // Мелкий размер блока позволяет P-ядрам украсть (work-stealing) до 75% работы
  items.par_iter()
       .with_min_len(16)
       .with_max_len(64)
       .for_each(|chunk| { ... });
  ```
- Механизм Chase-Lev deques в Rayon гарантирует: быстрое P-ядро будет автоматически воровать задачи из очереди медленного E-ядра, нивелируя разницу в тактовой частоте.

#### Режим 3: «Функциональная асимметрия» (Асинхронный пайплайн)
- **E-ядра (CPUs 8..11):** Токенизация текста, распаковка датасета Wikitext-2, дисковые операции, логирование метрик, подготовка батчей в памяти.
- **P-ядра (CPUs 0..7):** Матричное умножение (AVX2 GEMM), обратное распространение ошибки, обновление тернарных весов.
- Вычисления и подготовка данных перекрываются на 100%.

## 5. Флаги компилятора Rust (RUSTFLAGS) для пикового IPC

Для генерации машинного кода с максимальным IPC на архитектуре Raptor Lake компилятор LLVM должен знать точную модель микроархитектуры и доступные аппаратные инструкции.

### 5.1. Конфигурация Cargo (`.cargo/config.toml`)
Создайте или обновите файл в корне проекта:

```toml
[target.x86_64-pc-windows-msvc]
rustflags = [
    # Точечная оптимизация под микроархитектуру Raptor Lake
    "-C", "target-cpu=raptorlake",
    
    # Принудительная активация полного векторного набора
    "-C", "target-feature=+avx2,+fma,+bmi1,+bmi2,+lzcnt,+popcnt",
    
    # Слияние умножения и сложения в одну инструкцию FMA без промежуточного округления
    "-C", "llvm-args=-fp-contract=fast",
    
    # Агрессивный инлайнинг критических векторных функций
    "-C", "llvm-args=-inline-threshold=1000",
    
    # Разрешение развертки циклов под широкий конвейер (512 ROB entries)
    "-C", "llvm-args=-unroll-threshold=800",
    
    # Оптимизация линкера MSVC: удаление мертвого кода и объединение идентичных функций (ICF)
    "-C", "link-arg=/OPT:REF",
    "-C", "link-arg=/OPT:ICF=3",
]
```

### 5.2. Профиль сборки (`Cargo.toml`)
```toml
[profile.release]
opt-level = 3              # Максимальная оптимизация кода
lto = "fat"                # Глобальная межмодульная оптимизация (Link-Time Optimization)
codegen-units = 1          # Единый модуль генерации кода для максимального инлайнинга
panic = "abort"            # Удаление таблиц раскрутки стека (уменьшает размер и освобождает регистры)
strip = true               # Удаление отладочных символов из бинарника
overflow-checks = false    # Отключение проверок переполнения в горячих циклах
debug = false
```

### 5.3. Высокопроизводительный аллокатор памяти (Замена Windows Heap)
Стандартный аллокатор Windows (`HeapAlloc`) страдает от блокировок критических секций при параллельных аллокациях тензоров на 12 потоках. Обязательно подключение **mimalloc**:

```toml
# В dependencies Cargo.toml:
mimalloc = { version = "0.1", default-features = false }
```

```rust
// В main.rs или lib.rs:
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;
```
`mimalloc` устраняет блокировки страниц памяти и использует кэши свободных блоков на поток (thread-local slab cache), ускоряя создание тензоров на 30–45%.

## 6. Готовые программные реализации для проекта

### 6.1. Модуль привязки потоков к ядрам (Thread Affinity & QoS) под Windows
Файл `src/hardware.rs`:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use windows_sys::Win32::System::Threading::{
    GetCurrentThread, SetThreadAffinityMask, SetThreadPriority,
    THREAD_PRIORITY_HIGHEST,
};

/// Маски процессоров для i5-13420H
pub struct HardwareMasks;
impl HardwareMasks {
    /// 4 физических P-ядра (без SMT): CPU 0, 2, 4, 6 (маска: 0b01010101 = 0x55)
    pub const P_CORES_PHYSICAL: usize = 0x0055;
    
    /// Все логические потоки P-ядер (с SMT): CPU 0..7 (маска: 0b11111111 = 0xFF)
    pub const P_CORES_ALL: usize = 0x00FF;
    
    /// Все E-ядра (Gracemont): CPU 8..11 (маска: 0b111100000000 = 0x0F00)
    pub const E_CORES_ALL: usize = 0x0F00;
    
    /// Все доступные 12 потоков процессора
    pub const ALL_CORES: usize = 0x0FFF;
}

/// Настройка пула Rayon с автоматической привязкой к P-ядрам
pub fn init_pcore_threadpool(num_threads: usize) -> Result<rayon::ThreadPool, rayon::ThreadPoolBuildError> {
    static THREAD_COUNTER: AtomicUsize = AtomicUsize::new(0);
    
    rayon::ThreadPoolBuilder::new()
        .num_threads(num_threads)
        .thread_name(|i| format!("aiml-pcore-{}", i))
        .start_handler(move |_index| {
            unsafe {
                let thread = GetCurrentThread();
                
                // Приоритет реального времени для минимизации латентности
                SetThreadPriority(thread, THREAD_PRIORITY_HIGHEST);
                
                // Назначение потока на конкретное логическое P-ядро (0..7)
                let id = THREAD_COUNTER.fetch_add(1, Ordering::SeqCst) % 8;
                let mask = 1usize << id;
                SetThreadAffinityMask(thread, mask);
            }
        })
        .build()
}
```

### 6.2. Векторное AVX2 FMA микроядро ($6 \times 16$)
Файл `src/gemm_kernel.rs`:

```rust
#[cfg(target_arch = "x86_64")]
use std::arch::x86_64::*;

/// Оптимизированное микроядро 6x16 под Raptor Lake P-core
/// Аккумулирует 6x16 блок матрицы C за K шагов
#[target_feature(enable = "avx2", enable = "fma")]
pub unsafe fn microkernel_6x16(
    k: usize,
    a_ptr: *const f32, // Упакованный блок A (размер Mc x Kc, построчно)
    b_ptr: *const f32, // Упакованная панель B (размер Kc x Nc, столбцами по 16)
    c_ptr: *mut f32,   // Выходная матрица C
    ldc: usize,        // Ведущий шаг матрицы C
) {
    // 12 векторных аккумуляторов для сетки 6x16 (по 2 YMM на строку)
    let mut c00 = _mm256_setzero_ps(); let mut c01 = _mm256_setzero_ps();
    let mut c10 = _mm256_setzero_ps(); let mut c11 = _mm256_setzero_ps();
    let mut c20 = _mm256_setzero_ps(); let mut c21 = _mm256_setzero_ps();
    let mut c30 = _mm256_setzero_ps(); let mut c31 = _mm256_setzero_ps();
    let mut c40 = _mm256_setzero_ps(); let mut c41 = _mm256_setzero_ps();
    let mut c50 = _mm256_setzero_ps(); let mut c51 = _mm256_setzero_ps();

    let mut a_curr = a_ptr;
    let mut b_curr = b_ptr;

    // Внутренний цикл по K
    for _ in 0..k {
        // Загрузка двух 256-битных векторов из матрицы B (16 значений)
        let b0 = _mm256_loadu_ps(b_curr);
        let b1 = _mm256_loadu_ps(b_curr.add(8));

        // Строка 0: Бродкаст A[0, k] и FMA
        let a0 = _mm256_set1_ps(*a_curr);
        c00 = _mm256_fmadd_ps(a0, b0, c00);
        c01 = _mm256_fmadd_ps(a0, b1, c01);

        // Строка 1: Бродкаст A[1, k] и FMA
        let a1 = _mm256_set1_ps(*a_curr.add(1));
        c10 = _mm256_fmadd_ps(a1, b0, c10);
        c11 = _mm256_fmadd_ps(a1, b1, c11);

        // Строка 2: Бродкаст A[2, k] и FMA
        let a2 = _mm256_set1_ps(*a_curr.add(2));
        c20 = _mm256_fmadd_ps(a2, b0, c20);
        c21 = _mm256_fmadd_ps(a2, b1, c21);

        // Строка 3: Бродкаст A[3, k] и FMA
        let a3 = _mm256_set1_ps(*a_curr.add(3));
        c30 = _mm256_fmadd_ps(a3, b0, c30);
        c31 = _mm256_fmadd_ps(a3, b1, c31);

        // Строка 4: Бродкаст A[4, k] и FMA
        let a4 = _mm256_set1_ps(*a_curr.add(4));
        c40 = _mm256_fmadd_ps(a4, b0, c40);
        c41 = _mm256_fmadd_ps(a4, b1, c41);

        // Строка 5: Бродкаст A[5, k] и FMA
        let a5 = _mm256_set1_ps(*a_curr.add(5));
        c50 = _mm256_fmadd_ps(a5, b0, c50);
        c51 = _mm256_fmadd_ps(a5, b1, c51);

        a_curr = a_curr.add(6);
        b_curr = b_curr.add(16);
    }

    // Сохранение результатов обратно в память с добавлением старого значения C
    macro_rules! store_row {
        ($row:expr, $c0:expr, $c1:expr) => {
            let row_ptr = c_ptr.add($row * ldc);
            let prev0 = _mm256_loadu_ps(row_ptr);
            let prev1 = _mm256_loadu_ps(row_ptr.add(8));
            _mm256_storeu_ps(row_ptr, _mm256_add_ps(prev0, $c0));
            _mm256_storeu_ps(row_ptr.add(8), _mm256_add_ps(prev1, $c1));
        };
    }

    store_row!(0, c00, c01);
    store_row!(1, c10, c11);
    store_row!(2, c20, c21);
    store_row!(3, c30, c31);
    store_row!(4, c40, c41);
    store_row!(5, c50, c51);
}
```

## 7. Чек-лист оптимизации для разработчика

1. [x] **Изучена топология:** 4P ядра (`CPUs 0..7`) + 4E ядра (`CPUs 8..11`).

   - Использование динамического воровства задач (`Rayon with_min_len`) при совместной работе.
